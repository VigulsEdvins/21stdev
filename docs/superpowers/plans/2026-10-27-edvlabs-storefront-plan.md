# edvlabs storefront — epics, tasks and subtasks

Written 2026-10-27. Design and decisions: [../specs/2026-10-27-edvlabs-storefront-design.md](../specs/2026-10-27-edvlabs-storefront-design.md). Read that first; the decisions D1–D8 there are assumed here.
Status: **plan only, nothing built.** Items marked **[decision]** wait for you.

Size: S ≤ 0.5 day, M ≈ 1–2 days, L ≈ 3–5 days, XL > 1 week (split before starting). Priority: **P0** needed for the first public sale, **P1** needed for the self-serve path, **P2** after launch.
Every task has a **Done when** line. Nothing counts as done unless it is checked in a browser as the visitor would use it, and `npm run verify`, `npm test` and `npm run test:e2e` still pass.

## How the work is ordered

| Phase | Result | Epics | Rough size |
|---|---|---|---|
| **0. Decide and prepare** | Decisions D1–D8 answered, accounts opened, repo and environments ready, design direction chosen, **security tooling running in CI (E16.1–E16.4, E16.11)** | E0, E1 (direction only), E16 (baseline) | 1–2 weeks |
| **1. Sell by hand (done-for-you)** | A public site you can send people to. A visitor answers the questions and leaves a contact. You get the whole brief by email and see it in a simple list. No accounts, no payments | E1, E2, E3, E9 (lead part), E12 (minimum), E13, E14, **E16 (all except E16.9 depth)** | 5–7 weeks |
| **2. Sell self-serve** | Registration, the redesigned beginner builder, saved projects, price calculator, Stripe checkout, download after payment | E4, E5, E6, E7, E8, E10, E11, **E16.9, E16.14 (second round)** | 8–12 weeks |
| **3. Harden and grow** | Server-side export (real paywall), hosting, quotes as PDF, translations, analytics-driven fixes | E15 | ongoing |

Why this order: the done-for-you path needs only email, and it is the path where you earn more per customer. It will also show which questions people answer, which sections they ask for and what they are willing to pay, before the self-serve half (the expensive half) is built.

Dependency sketch (arrow = "needs"):
`E0 → everything` · `E1 → E2, E3, E6, E10` · `E3 → E9, E5` · `E4 → E7, E8, E10` · `E5 → E3 (price preview), E6, E8` · `E7 → E8` · `E12 → E14` · `E13` runs alongside all · `E16` runs alongside all and **gates** E14 (launch) and E8 (real payments).

## E3 — The guided questions ("brief") and recommendation (P0)

Goal: a short conversation that collects what you need, never blocks someone who does not know, and ends in a clear choice.

- **E3.1 Write the questions (M) [decision].**
  - Subtasks: draft about 10 questions, each with a plain explanation and an **"I don't know yet"** answer that is a first-class choice (never an error); proposed list: (1) What is the page for: my business / myself / an event / a product / something else; (2) What kind of business or work; (3) What should a visitor do on the page (call, book, buy, sign up, read about me, see my work); (4) Which blocks of the page do you want — shown as simple cards with a one-line explanation and a tiny picture (opening banner, about, services, prices, gallery, reviews, questions and answers, contact form, map and opening hours, newsletter sign-up, team, process, footer) plus "not sure, suggest for me"; (5) Do you want to be able to change the text yourself later (the editor): yes / no / not sure (with a plain explanation of what it is); (6) Do you already have text, photos and a logo: all / some / none; (7) Feel and style: pick up to three words and optionally paste links of sites you like; (8) How many languages; (9) Do you already have a domain and hosting; (10) When do you need it and what budget range; (11) Last: **Do you want to build it yourself (no code) or should edvlabs do the work for you?** with the price shown for each.
  - Done when: you approved the final wording; every question has an "I don't know" path.
- **E3.2 Data model for an answer (S).** Subtasks: define the brief as one JSON document with a version number (`brief_v1`), each answer as `{ value, unknown: true|false, note }`; define the allowed values for each question; write a JSON schema; write sample briefs (complete, mostly "I don't know", contradictory). Done when: the schema validates all samples and rejects malformed ones.
- **E3.3 Wizard screen flow (L).**
  - Subtasks: one question per screen with a progress indicator, "Back" and "Skip", answers kept in the browser as the visitor goes (survive refresh and the back button); keyboard and screen-reader friendly (radio cards are real radios); mobile first; a "save and finish later" that emails a link (Phase 2) or keeps it in the browser (Phase 1); a summary screen where each answer can be edited; clear wording at the choice point (E3.7).
  - Done when: a test visitor finishes the questions in under 4 minutes on a phone, including at least three "I don't know" answers.
- **E3.4 Recommendation rules (L).**
  - Subtasks: map (purpose × industry × goal) to a starting list of sections, reusing `scripts/builder/starters.js` and the registry's industry and mood tags; when the visitor says "I don't know", choose the safest set (opening banner, about, services, reviews, contact); add or remove sections according to answers (a booking goal adds a booking or contact block; a shop goal adds product cards); stay within a sensible count; explain each suggestion in one line ("because you want people to call you"); keep rules in a table (data, not code) so you can change them.
  - Done when: ten different sample briefs each give a sensible page of 5–9 sections and a test checks that every recommended section exists, is not a draft and is not `heavy`.
- **E3.5 Live price preview inside the wizard (M).** Subtasks: show a running estimate from question 4 onward ("about €X for yourself, from €Y if we do it"); explain it in a sentence; never show a price the calculator (E5) did not produce. Done when: the estimate in the wizard equals the quote at the end for the same inputs (test).
- **E3.6 Storing and sending the brief (M).**
  - Phase 1 (done-for-you only): on submit, send the brief to a form endpoint (a Supabase table through a small function, or a hosted form service as a stop-gap) and email it to you; store it in the lead list (E9).
  - Phase 2: the brief is attached to the account and pre-fills the builder (E6.1).
  - Subtasks: validation on the server; rate limiting and a spam check (honeypot plus Cloudflare Turnstile); consent checkbox with a link to the privacy notice; save a copy of what the visitor agreed to; confirmation screen and email to the visitor.
  - Done when: a submitted brief appears in the owner's inbox and list within a minute, with every answer readable and "I don't know" marked clearly.
- **E3.7 The fork: do it yourself or we do it (S).** Subtasks: two equal choices with plain text, what you get, what it costs, how long it takes, what you need to do; the chosen path decides the next screen (register for self-serve; contact details for done-for-you); a third quiet link "I want to talk first". Done when: tested with five people who understand the difference without help.
- **E3.8 Done-for-you contact step (S).** Subtasks: ask for an email **or** a phone number (at least one); preferred way and time to be contacted; optional name; one consent checkbox; thank-you page that says exactly what happens next and when. Done when: submission with only a phone number works and the owner email shows how to reach them.

## E5 — Price model and calculator (P0 for display, P1 for charging)

- **E5.1 Define the price model (M) [decision].**
  - Subtasks: write the formula you want (proposal: base + per-section price above N included sections + admin-editor add-on + optional extras: multi-page, extra language, review copy); decide volume steps; decide what counts as a section (each block in the builder's list; hidden sections do not count; the header and footer count or are included); decide the done-for-you work fee (per section by complexity: `light / medium / heavy` weight already exists in the registry, plus fixed fees for the editor and for each extra page and language); decide discounts and promo codes; decide VAT display; decide currency and rounding; decide what happens when someone adds sections after paying (pays the difference).
  - Done when: a worked-example table (10 cases) is signed off by you.
- **E5.1a Market price check (S).** Subtasks: the first lookup is in the design doc §11 (Wix, Squarespace, Webflow, Framer, Carrd, Mozello, templates, freelancers); confirm each number on the vendor's own page; collect real quotes for the same 6-block page from 3 local freelancers or agencies; note the date; repeat yearly. Done when: the E5.1 worked examples sit inside the market range with a stated margin.
- **E5.2 Price table as data (S).** Subtasks: a versioned `pricing_config` row and a JSON file with the same shape for local use; every price in euro cents; all labels in one place; a changelog; you can edit it in the owner admin (E9.5) without code. Done when: changing a value changes every place that shows a price (test).
- **E5.3 One calculator module (M).**
  - Subtasks: a small pure JavaScript module `price.js` used by the wizard, the pricing page, the builder meter, the quote email and the server; inputs: number of sections, editor yes/no, extras, path (self / done-for-you), voucher; output: line items, subtotal, VAT, total, and the price-table version; unit tests including edge cases (0 sections, many sections, hidden sections, rounding); a test that runs the same cases against the browser build and the server build.
  - Done when: the cases from E5.1 pass and the browser and server give identical numbers. It also prices **an upgrade**: given the allowance already paid, the blocks now counted and the editor flag, it returns only the difference at the locked price version (D7a), and nothing when the count is at or below the allowance.
- **E5.4 Quotes (M).** Subtasks: store a quote with its inputs and the price-table version so it can be honoured for 14 days; show it as a page and email it; the quote is what checkout charges (recomputed on the server from the project, never trusted from the browser). Done when: tampering with the price in the browser does not change the charged amount (test).
- **E5.5 Section counter and live meter in the builder (S).** Subtasks: count visible sections; show "7 blocks · €X" with a one-line breakdown on hover; warn before a change crosses a price step; show it in the export step. Done when: adding, hiding, removing and undoing sections updates the meter immediately. For a paid page the meter reads "5 of 5 blocks paid for" and shows a price only for blocks above that (D7a).

## E6 — The builder for non-technical people (P1; the redesign of `index.html` and `builder.html`)

Goal: a stranger can choose blocks, write their text and set the look without help. The current screen shows everything at once (255 items, mood/industry/weight filters, "Target section", "Widgets vs Sections"); the new default shows a guided path, and the old power is behind an "Advanced" switch.

- **E6.1 Entry: start from the brief (M).**
  - Subtasks: open the builder with the recommended sections from the brief (E3.4) or from a chosen example (E2.4); a "start from scratch" option; a short first-time message instead of the current tour; project is created in the account automatically.
  - Done when: from the end of the wizard to a filled builder takes one click.
- **E6.2 The guided path: five steps with a simple progress bar (L) [design first].**
  1. *Blocks*: choose and order the blocks of the page.
  2. *Words*: write your text and add your photos.
  3. *Look*: pick a colour set, a font pair, the roundness.
  4. *Check*: preview on desktop, tablet and phone; checklist of problems.
  5. *Get it*: price, choose the editor yes/no, pay, download.
  - Subtasks: each step is one screen with one job and a visible "Next"; the user can jump back; the existing advanced panels (Elements, Sections, Styling, Content) are reachable from an **Advanced** switch and remember the choice; keyboard shortcuts stay.
  - Done when: five people who never saw it can finish a page with their own text without asking anything (E13.6).
- **E6.3 Step 1 — Blocks: a plain block picker (L).**

## E16 — Security checks for all code (P0; automated in CI, reviewed by hand before launch)

Goal: every line that ships or runs — the 235 components, the builder and its scripts, the storefront, the server functions, the CI and the infrastructure — is checked automatically on every change and reviewed by a person before the first public sale. One command (`npm run security`) runs everything that can run locally; CI runs it on every pull request and nightly.

What exists today (and is kept): `scripts/check-code-safety.js` (no `eval`, `new Function`, `document.write`, remote scripts from non-allowed hosts, `message` listeners without an origin check — for `features/` only); a Content-Security-Policy on `index.html` and `builder.html` (it still allows `'unsafe-inline'` scripts because the preview frame inherits it); the project-import sanitiser (`scripts/project-sanitize.js`); the dev server's path guard; `npm audit` (informational only, in the reports job); a strict-CSP export option; a code-safety scan inside `npm test`. A first read-only look found no secret-like strings in tracked files, **58 `innerHTML =` assignments, 10 `postMessage` uses and 30 `localStorage` uses in the builder code** that have never been reviewed one by one, and a preview frame with `sandbox="allow-scripts allow-same-origin"` (see E16.5).

Severity policy used by every task below: **critical** (account takeover, payment bypass, secret leak) fixed within 24 hours and blocks release; **high** fixed before the next release; **medium** within 30 days; **low** tracked. A finding may be waived only with a written reason and an expiry date (the same idea as `safetyReviewed` in `meta.json`).

- **E16.1 Scope, inventory and threat model (M).**
  - Subtasks: list every kind of code and who wrote it (own components, rewritten components, builder scripts, storefront pages, server functions, CI workflows, build scripts, third-party libraries, the three outside-folder templates); mark what runs in the visitor's browser, what runs on the server and what only runs on your machine; draw the data flows (brief → lead, account → project, project → payment → download, owner area); for each flow list what an attacker could try (spoofing, tampering, leaking data, denying service, gaining rights) and what stops them; write it down in `docs/security/threat-model.md`; list assets worth protecting (customer data, payment state, the price table, the owner login, the source of the templates).
  - Done when: every flow in the plan has a short threat list with a named control, and you have read and approved it.
- **E16.2 Secrets (S, do first). Status 2026-10-27: scanner, pre-commit hook, history scan and CI job done (`npm run check-secrets`, `.githooks/`); still to do: turn on the Git host's secret scanning and push protection, the table of secrets, and the built-file key check once there is a storefront build.**
  - Subtasks: add a secret scanner (gitleaks) as a pre-commit hook and as a CI job; scan the **whole git history once** (not only the latest files) and rotate anything found; turn on the Git host's secret scanning and push protection if available; add a check that fails when a built page or script contains something that looks like a key (`sk_live`, `service_role`, long random strings next to `key`/`token`); keep `.env` files out of git and out of deploy bundles; list every secret in a table (what, where it lives, who can read it, how to rotate it); never place the Supabase service key or the Stripe secret key in any browser file.
  - Done when: a deliberately planted fake key in a test branch is blocked by the hook and by CI, and the history scan is clean or fully rotated.
- **E16.3 Dependencies and supply chain (M). Status 2026-10-27: lock file committed, CI uses `npm ci` with read-only permissions, `npm run audit` blocks at high and critical in the new `security` job; still to do: update pull requests (Dependabot or Renovate), OSV-Scanner, pinning actions to commit hashes, SBOM, licence allow-list, replacing remote script hosts.**
  - Subtasks: make the lock file part of the repository and install with `npm ci` everywhere (today `package-lock.json` is listed in `.gitignore` and **no lock file is committed**, and CI runs `npm install`, so every build can pull different versions; remove it from `.gitignore`, commit the lock file and switch CI to `npm ci`); make `npm audit --omit=dev` **blocking** at high and critical (it is informational now); turn on automatic weekly dependency update pull requests (Dependabot or Renovate) with the tests as the gate; add OSV-Scanner as a second opinion; keep dev-only tools (Playwright, esbuild, Lighthouse) out of the production dependency list and out of deploys; pin every GitHub Action to a full commit hash and give each workflow the least permissions (read-only by default); do not run install scripts of new packages without review (`--ignore-scripts` where possible); write a short "adding a dependency" checklist (maintained? downloads? licence? install scripts? size?); produce a software bill of materials (CycloneDX) on each release; check dependency licences against an allow-list; replace remote script and style hosts (cdnjs, jsdelivr, unpkg, Google Fonts) in the storefront and in exports by self-hosted copies, or add Subresource Integrity hashes where a remote file must stay.
  - Done when: a pull request that adds a package with a known high vulnerability fails CI, and `docs/dependencies.md` lists every runtime dependency with its reason.
- **E16.4 Static analysis of all code (L).**
  - Subtasks: add Semgrep (security and JavaScript/TypeScript rule packs) over `scripts/`, `builder.js`, `app.js`, the storefront, the server functions and `features/`; add ESLint with the security and no-unsanitized plugins to the same folders; turn on GitHub CodeQL if the plan allows it; extend `scripts/check-code-safety.js` from `features/` to every folder, with rules for: `innerHTML`/`outerHTML`/`insertAdjacentHTML` with non-constant input, `javascript:` and `data:` URLs built from input, `setTimeout`/`setInterval` with strings, `postMessage` with `'*'` as target, `message` listeners without origin checks, `target="_blank"` without `rel="noopener"`, regexes that can run forever on long input (ReDoS), prototype pollution patterns (`Object.assign` or merge into `{}` from input, `__proto__`), unsafe `JSON.parse` of storage without a try/catch, file paths built from input, `child_process`/`exec` with input, `Math.random` for anything secret; run once, triage the first results into "fix", "false positive (with reason)" and "accept (with expiry)", and store the baseline so that CI fails only on **new** findings.
  - Done when: `npm run security:static` runs in under 3 minutes, the baseline is committed, and a test pull request adding an unsafe `innerHTML` is blocked.
- **E16.5 Review of the risky spots found so far (L).**
  - Subtasks: go through all **58 `innerHTML =` sites** and mark each as safe (constant or escaped), fixed (switch to `textContent` or to element creation) or waived with a reason; review the **10 `postMessage` handlers** for origin and shape checks; review the **30 `localStorage` uses**: what is stored, whether anything sensitive will live there once accounts exist (never store session tokens or personal data in `localStorage`; use secure, `HttpOnly`, `SameSite` cookies set by the auth service), and that corrupt or hostile stored data cannot break or exploit the page (autosave recovery exists); decide the **preview frame** question: today the preview is an `iframe` with `allow-scripts allow-same-origin`, which means code inside a section can reach the builder page, its storage and, later, the account session. Options: (a) serve the preview from a separate domain that holds nothing, (b) drop `allow-same-origin` and talk to the preview only through `postMessage`, (c) accept for the vault's own components only and block it for anything a customer pasted. Choose one and write down why; review every place customer-written content reaches the preview or the export (text overrides, link values, image addresses, favicon, JSON-LD, page title and description, business fields, review comments, imported project files, uploaded SVGs) for HTML, script and URL injection; make sure `javascript:`, `vbscript:` and non-image `data:` values are refused in every one of those places (the import sanitiser already does this for imports).
  - Done when: a table lists every reviewed site with its verdict, no unreviewed `innerHTML` remains, and a hostile-input test file (HTML in every text field, `javascript:` links, a script inside an SVG, oversized values, a prototype-pollution key) is added to the test suite and passes.
- **E16.6 Security regression tests (L).** **Status 2026-10-29: R01 to R16 for what exists (`docs/security/regression-map.md`); the rest waits for checkout, webhooks and the owner area.**
  - Subtasks: unit and browser tests that fail when a protection is removed: hostile project import (exists, extend), hostile content overrides, hostile review-comment files, path traversal on the dev server and on every file-serving function, price tampering (the browser sends a lower price; the server charges the real one), access to another customer's project or order by changing an id (IDOR), reading rows without being signed in, owner-only pages opened by a customer, webhook with a wrong signature and a replayed webhook, rate limits on sign-in and on the brief and contact forms, spam through the honeypot, email header injection in form fields, open redirect in the payment success address, CSRF on state-changing requests, upload of a disallowed type and of an oversized file, download link after refund and after expiry.
  - Done when: each item above has a named test, all run in CI, and removing the matching protection in a trial branch makes exactly that test fail.
- **E16.7 Headers and Content Security Policy for the storefront and builder (M).** **Status 2026-10-29: report-only policy on the builder, probe script, plan in `docs/security/builder-csp.md`; enforcing needs the preview frame moved.**

- **E16.8 Dynamic testing (M).** **Status 2026-10-29: fuzzing runs in `npm test`; the ZAP workflow waits for `STAGING_URL`.**

- **E16.9 Server and API security (L) (Phase 2; the baseline in Phase 1).**

## Risks and what to do about them

| Risk | Why it matters | Plan |
|---|---|---|
| Browser-side export can be bypassed | A paid site could be taken without paying | Soft paywall first (E7.3), server build later (E7.4); watermark unpaid previews |
| Tax and invoice rules for selling digital goods in the EU | A mistake costs money and trust | Accountant before the first sale (E0.2); consider a merchant of record (E8.1) |
| Personal data in briefs and accounts | Fines and loss of trust | Minimal collection, clear notice, deletion path, EU region (E12) |
| Done-for-you work grows without limit | Time is your most expensive resource | Fixed scope per price line; "what is not included" on the page; revision limit in the terms |
| "Admin panel" is understood as a login CMS | Disappointed customers and refunds | Name it "Editor", describe it exactly (E11.1) |
| The redesign takes longer than the rest | The product looks unfinished | Choose the direction early (E1.2); tokens first; reuse the builder, redesign its skin and flow, not its engine |
| Too many options confuse beginners | They leave | The five-step path hides advanced options; usability tests (E13.6) |
| Outside-folder templates missing in production | Broken "Full Websites" | E0.6 and a deploy check |
| One-person bottleneck | Slow replies lose sales | Support routine, templates, a response-time promise you can keep (E14.6) |
| Vendor lock-in | Hard to move later | Plain Postgres, exportable data, no proprietary formats for projects |
| A customer's pasted content or a hostile project file runs script in the builder (the preview frame shares the builder's origin) | Account or session theft once accounts exist | Decide and fix the frame isolation (E16.5) before accounts go live; sessions in `HttpOnly` cookies, never in `localStorage` |
| A secret ends up in git, a browser file or a deploy | Payment or data compromise | Secret scanning in hook and CI, history scan, deploy allow-list (E16.2, E16.11) |
| A vulnerable or hijacked dependency | Supply-chain attack | Lock file, blocking audit, pinned actions, update PRs, SBOM (E16.3) |
